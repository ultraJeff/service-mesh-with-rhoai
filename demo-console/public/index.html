      2
      Why Does This Matter?
      2 min
    

    

      

        RHOAI 3.4 provides TLS at the ingress layer and optional auth via enable-auth: true.
        For most deployments, this is sufficient. For regulated and high-security environments
        that require mutual authentication, workload identity, and east-west encryption —
        we harden RHOAI with a service mesh.
      


      

        What the service mesh adds:

        

          
CapabilityRHOAI AloneRHOAI + Mesh

          
Ingress TLSYesYes (custom CA)

          
Mutual authenticationNoYes (mTLS)

          
Workload identityNoYes (SPIFFE)

          
East-west encryptionNoYes (ztunnel)

          
Customer-managed CANoYes (cert-manager)

          
L7 authorization policyNoYes (waypoint)

        

      

    

  


  
  

    

      3
      How It Works — Ambient Mesh
      3 min
    

    

      

        OSSM v3 ambient mode. No sidecars, no app changes.
        ztunnel runs per-node and transparently intercepts all pod traffic.
        Apps serve plain HTTP internally — but nothing crosses the network unencrypted.
        Enrollment is two namespace labels.
      


      

        Where is traffic encrypted?


        Pod A (node 1)

          app → plain HTTP → ztunnel (same network namespace, never leaves the pod)

            ↓

          ===== HBONE mTLS on port 15008 (encrypted on the wire) =====

            ↓

        Pod B (node 2)

          ztunnel → plain HTTP → app (same network namespace, never left the pod)


        The “plain HTTP” only exists between ztunnel and the app inside the same pod —

        like two processes on localhost. All pod-to-pod traffic is mTLS.


        Can we encrypt further?

        

          
LayerWhatCovers

          
ztunnel mTLSPod-to-pod on the wireAutomatic, no app changes

          
enable-authkube-rbac-proxy inside podOAuth token validation + TLS

          
App-level TLSModel runtime (--ssl-certfile)Last inch inside the pod

        

        
Each layer is additive. The intra-pod segment is between processes in the same

        network namespace. An attacker there has root on the pod — that’s a runtime

        security boundary (Falco, ACS), not a network security boundary.

      4
      Customer-Controlled Certificates
      3 min
    

    

      

        All mesh certificates — the gateway cert, every workload SPIFFE identity —
        chain to a single customer-controlled root CA.
        cert-manager handles the full lifecycle. In production, you swap the root with your corporate PKI.

SPIFFE workload identities (auto-assigned by istiod)

        
      

      


      

        Going further: Zero Trust Workload Identity Manager


        Currently, istiod is the CA that signs these SPIFFE identities from the
        cacerts secret. For organizations that need centralized identity governance,
        hardware-based attestation, or cross-cloud federation, istiod can be configured to
        delegate identity issuance to a SPIRE server.


        Red Hat's
        Zero Trust Workload Identity Manager
        provides this as a managed operator:

        

          Current:   cacerts secret → istiod (built-in CA) → SPIFFE certs

          With ZTWIM: SPIRE server → istiod (as agent) → SPIFFE certs


        Same SPIFFE format, same ztunnel mTLS — but adds hardware root of trust,
        cross-cloud federation, and centralized identity governance.

      L7 Authorization — Who Can Call the Model?
      3 min
    

    

      

        Beyond encryption: authorization policy.
        What if a compromised pod tries to call the model endpoint directly?
        The waypoint proxy enforces L7 rules based on SPIFFE identity.
        Watch: we restrict the model to gateway-only access. Other pods get 403 Forbidden.
