      Why Does This Matter?
      2 min
    

    

      

        RHOAI already uses Service Mesh 3 for ingress via the Gateway API —
        it handles north-south traffic routing and OAuth authentication out of the box.
        For regulated and high-security environments that also require mutual authentication,
        workload identity, and east-west encryption, we extend this with the ambient mesh.
      


      

        Service mesh capabilities:

        

          
CapabilityWhat it does

          
Mutual authentication (mTLS)Both sides of every connection prove their identity

          
Workload identity (SPIFFE)Every pod gets a cryptographic identity based on its service account

          
East-west encryptionAll pod-to-pod traffic encrypted transparently via ztunnel

          
L7 authorization policyControl which workloads can call which services, by identity

          
Traffic resilienceRetries, timeouts, circuit breaking — no app changes

          
ObservabilityTopology visualization, metrics, distributed tracing via Kiali

        Deep dive: BackendTLSPolicy (coming in OCP 4.22+)
        

          

            The integration challenge today:

              The RHOAI gateway (OCP Gateway API) and our ambient mesh

              are two separate Istio control planes. The OCP gateway

              cannot speak mTLS to mesh-enrolled backends because they

              have different trust domains (OCPBUGS-82544).


            Current approach:

              We deploy a mesh gateway (GatewayClass: istio) that is

              part of the ambient mesh and speaks mTLS to backends.

              For models with enable-auth: true, a separate mesh-internal

              Service routes traffic from the mesh gateway to the app container.


            Simplification: BackendTLSPolicy (Gateway API v1alpha3)

              Expected in OCP 4.22. Lets the OCP gateway natively connect

              to mesh-enrolled backends over TLS — eliminating the need

              for the separate mesh-internal Service.


              apiVersion: gateway.networking.k8s.io/v1alpha3

              kind: BackendTLSPolicy

              spec:

                targetRefs:

                  - kind: Service

                    name: iris-onnx-predictor

                validation:

                  caCertificateRefs:

                    - name: mesh-root-ca-secret

                      kind: Secret


            This simplifies the ingress path but does NOT replace the mesh.

            The ambient mesh is still required for east-west mTLS, SPIFFE

            identity, AuthorizationPolicy, and multi-cluster federation.

            BackendTLSPolicy bridges ingress to mesh — it is not the mesh itself.

            RFE-9140 tracks this for RHOAI + OSSM integration.
          

        

      

    

  


  
  

    

      3
      How It Works — Ambient Mesh
      3 min
    

    

      

        OSSM v3 ambient mode. No sidecars, no app changes.
        ztunnel runs per-node and transparently intercepts all pod traffic.
        Apps serve plain HTTP internally — but nothing crosses the network unencrypted.
        Enrollment is two namespace labels.
      


      

        Where is traffic encrypted?


        Pod A (node 1)

          app → plain HTTP → ztunnel (same network namespace, never leaves the pod)

            ↓

          ===== HBONE mTLS on port 15008 (encrypted on the wire) =====

            ↓

        Pod B (node 2)

          ztunnel → plain HTTP → app (same network namespace, never left the pod)


        The “plain HTTP” only exists between ztunnel and the app inside the same pod —

        like two processes on localhost. All pod-to-pod traffic is mTLS.


        Can we encrypt further?

        

          
LayerWhatCovers

          
ztunnel mTLSPod-to-pod on the wireAutomatic, no app changes

          
enable-authkube-rbac-proxy inside podOAuth token validation + TLS

          
App-level TLSModel runtime (--ssl-certfile)Last inch inside the pod

        

        
Each layer is additive. The intra-pod segment is between processes in the same

        network namespace. An attacker there has root on the pod — that’s a runtime

        security boundary (Falco, ACS), not a network security boundary.

        Deep dive: What happens when a pod starts in the mesh?
        

          

            Pod startup flow (6 steps):


            1. Pod created in an ambient-enrolled namespace


            2. istio-cni (DaemonSet on the node) detects the new pod

              istio-cni watches the kubelet for pod events on its node


            3. istio-cni enters the pod's network namespace using nsenter

              and injects iptables rules that redirect all traffic to ztunnel:


              
              # Equivalent to:

              nsenter --net=/proc/<pod-pid>/ns/net iptables -t nat ...

              

              # Rules injected:

              PREROUTING: redirect inbound TCP → ztunnel port 15006

              OUTPUT:     redirect outbound TCP → ztunnel port 15001

              PREROUTING: exempt kubelet probes (169.254.7.127) → ACCEPT

            

              The pod has no sidecar, no extra container. istio-cni reaches

              into the pod's network namespace from outside (it runs as a

              privileged DaemonSet with access to /proc). The pod never

              knows it happened.


            4. ztunnel (DaemonSet on the node) starts handling traffic

              for this pod. It's already listening on ports 15006/15001

              and can access all pod network namespaces on the node.


            5. ztunnel requests a SPIFFE certificate from istiod

              for this pod's identity (namespace + service account).

              istiod validates via K8s TokenReview, signs the cert with

              the intermediate CA, and returns it.


            6. Traffic flows:

              app → iptables redirect → ztunnel → HBONE mTLS →

              remote ztunnel → destination app


            What is a network namespace?


              A Linux kernel feature that gives a process its own isolated

              network stack — interfaces, IPs, routing tables, iptables, ports.

              Every pod in Kubernetes gets one. That's why two pods can both

              listen on port 8080 without conflicting.


              When ztunnel and the app "share a network namespace," traffic

              between them is like two processes on localhost — it never

              touches a physical interface. Traffic between pods crosses

              namespace boundaries and goes over the network — that's what

              ztunnel encrypts.


            Think of it as: istio-cni is the plumber that connects the pipes.

            ztunnel is the water treatment plant that all the pipes flow

            through. Neither lives in your house (pod) — they're shared

            infrastructure on each block (node).
          

        

      


      

        Deep dive: ztunnel vs Envoy in ambient mesh
        

          

            Two proxy technologies in ambient mesh:


            ztunnel (Rust, L4)

              DaemonSet — one per node, shared by all pods

              Handles: mTLS, HBONE tunnels, TCP metrics, L4 AuthZ (identity + port)

              Cannot: inspect HTTP headers, route by path, retries, rate limits

              Lightweight — no Envoy overhead per pod

              This is what makes ambient different from sidecar mode


              Both ztunnel and Envoy get config from istiod via xDS

              (a gRPC protocol for pushing config to proxies).

              Envoy gets full L7 config (routes, listeners, clusters).

              ztunnel gets only what it needs:

                • Workload discovery (pod IPs, namespaces, service accounts)

                • L4 authorization rules (who can connect to whom)

                • SPIFFE certs (via SDS)


            Envoy (L7)

              Only deployed where L7 capabilities are needed

              Shows up in two roles, both created via Gateway API:


                Waypoint proxy (GatewayClass: istio-waypoint)

                  East-west L7 policy inside the mesh

                  Handles: AuthorizationPolicy, retries, timeouts

                  Created by applying a Gateway CR in the app namespace

                  Opt-in per namespace — see Part 6 deep-dive for details


                Mesh gateway (GatewayClass: istio)

                  North-south ingress for external traffic

                  Handles: TLS termination, HTTP routing via HTTPRoutes

                  Created by applying a Gateway CR in istio-system

                  Has its own SPIFFE identity for mTLS to backends


              Both are Gateway API resources — same K8s standard,

              different GatewayClass, different role.

              Istio deploys an Envoy pod for each one automatically.


              Hot config: Envoy never reads static config files.

              istiod pushes updates via xDS over gRPC. When something

              changes (new HTTPRoute, new pod, rotated cert), Envoy

              applies it live — no restart needed.


            How do network layers work together?

            
L7 (HTTP request)      ← waypoint sees this (optional)
L4 (TCP connection)    ← ztunnel encrypts this (always)
L3 (IP routing)        ← Kubernetes CNI handles this
L2 (Ethernet frames)   ← physical/virtual network

              The layers are a stack, not alternatives. L7 rides on

              top of L4. You can't have an HTTP request without a TCP

              connection underneath. When the waypoint handles L7,

              ztunnel is still handling L4 mTLS on both hops.


            What is HBONE?

              HTTP-Based Overlay Network Encapsulation.

              An HTTP/2 CONNECT tunnel with mTLS on port 15008.

              ztunnel wraps pod traffic inside this tunnel —

              the original TCP connection rides inside an encrypted

              HTTP/2 stream between nodes. This is what makes

              ambient mesh encryption transparent to applications.


            In sidecar mode, every pod gets Envoy. In ambient mode,

            Envoy is opt-in (waypoints + gateways only). ztunnel (Rust)

            handles the common case (L4 mTLS) with much less overhead.
          

        

      


      

        Deep dive: How does sidecar mesh work? (and why ambient is different)
        

          

            Sidecar mode (traditional Istio / OSSM 2.x):


              Every pod gets an Envoy proxy container injected alongside

              the application container. The two containers share a network

              namespace. All inbound and outbound traffic goes through Envoy.


            
Pod A (node 1)                Pod B (node 2)
┌────────────────────┐        ┌────────────────────┐
│ App ←→ Envoy       │        │ Envoy ←→ App       │
│ (localhost,        │        │ (localhost,        │
│  shared netns)     │        │  shared netns)     │
└─────────┬──────────┘        └─────────┬──────────┘
          │                             │
          └──── mTLS (direct TLS) ──────┘
            regular pod network (CNI)
            no special mesh network

              In sidecar mode, Envoy does the mTLS directly — it holds

              the SPIFFE cert and does the TLS handshake over the normal

              pod network (OVN, Calico, whatever CNI is installed).

              No special network, no HBONE — just TLS on the existing wires.

              Pros: Full L7 on every connection (retries, routing, AuthZ)

              Cons: Extra CPU/memory per pod, sidecar injection required,

                    pods must restart to add/remove the sidecar


            Ambient mode (OSSM 3.x):


              No sidecar. ztunnel runs per-node (DaemonSet) and handles

              L4 mTLS for all enrolled pods transparently. Envoy only

              appears as waypoint proxies (opt-in, for L7 policy) and

              the mesh gateway (for north-south ingress).


            
┌────────────────┐  ┌────────────────┐
│ Pod A          │  │ Pod B          │
│ (app only,     │  │ (app only,     │
│  no sidecar)   │  │  no sidecar)   │
└───────┬────────┘  └───────┬────────┘
        │ iptables          │ iptables
        ▼                   ▼
┌────────────────────────────────────┐
│ ztunnel (shared, per-node)         │
│ handles mTLS for all pods          │
└────────────────────────────────────┘

              Pros: No per-pod overhead, no injection, no restarts,

                    enrollment is a namespace label

              Cons: L7 requires deploying a waypoint proxy


            Can sidecar and ambient coexist?


              Yes. Sidecar and ambient can coexist in the same mesh.

              Label each namespace for one mode only — either

              istio-injection=enabled (sidecar) or

              istio.io/dataplane-mode=ambient (ambient).

              Both share the same Istio control plane and CA trust chain.


              This matters for gradual migration: you can move namespaces

              from sidecar to ambient one at a time, or keep some on

              sidecar if they need features that require it.

        Deep dive: ReferenceGrants (Gateway API cross-namespace trust)
        

          

            Problem: Gateway API is strict about cross-namespace references.

            An HTTPRoute in namespace A can reference a Gateway in namespace B

            (if the Gateway allows it), but a Gateway in namespace A cannot

            route to a Service in namespace B without explicit permission.


            Solution: ReferenceGrant

            A ReferenceGrant in the target namespace says:

              "I allow resources of type X from namespace Y to reference

              my Services (or Secrets, etc.)"


            Example:

            
              apiVersion: gateway.networking.k8s.io/v1beta1

              kind: ReferenceGrant

              metadata:

                name: allow-gateway-to-model

                namespace: super-slim-demo

              spec:

                from:

                  - group: gateway.networking.k8s.io

                    kind: HTTPRoute

                    namespace: istio-system

                to:

                  - group: ""

                    kind: Service

            

            In our setup:

              Our HTTPRoutes are in super-slim-demo (same namespace as

              the Services), so no ReferenceGrant is needed for backendRefs.

              The Gateway in istio-system allows routes from all namespaces

              via allowedRoutes.namespaces.from: All.


            ReferenceGrants become important when the Gateway and Services

            are in different namespaces — common in multi-team environments

            where platform teams own the gateway and app teams own the services.

        Deep dive: PeerAuthentication
        

          

            PeerAuthentication controls whether pods accept non-mTLS traffic:


            STRICT (what we use)

              Every inbound connection MUST present a valid SPIFFE cert.

              Plain HTTP is rejected. No exceptions.

              This is what enforces zero trust — if you're not in the

              mesh, you can't talk to these pods.


            PERMISSIVE (migration mode)

              Accept both mTLS and plain HTTP.

              Useful during migration when some traffic sources

              aren't in the mesh yet (e.g., RHOAI gateway before

              we deployed our mesh gateway).


            DISABLE

              No mTLS enforcement. Not recommended.


            Scope: can be set per-namespace, per-workload, or even

            per-port. Example: we allow PERMISSIVE on port 8082

            (Prometheus metrics) while keeping STRICT on port 8080

            (model serving) — so Prometheus can scrape without

            being in the mesh.

        Deep dive: How the waypoint proxy works
        

          

            The waypoint is an Envoy proxy enrolled in the mesh.

            It has its own iptables rules, its own SPIFFE identity,

            and ztunnel encrypts its traffic just like any other pod.


            Traffic flow (two separate mTLS hops):


            
Pod A (app sends HTTP)
  │
  ▼
ztunnel (node A)
  │
  │  ══ HBONE mTLS hop 1 ══
  │
  ▼
ztunnel (waypoint node)
  │
  ▼
┌─────────────────────────┐
│ Envoy (waypoint)        │
│  checks AuthZ policy    │
│  applies retries/timeout│
└────────────┬────────────┘
             │
             ▼
ztunnel (waypoint node)
  │
  │  ══ HBONE mTLS hop 2 ══
  │
  ▼
ztunnel (node B)
  │
  ▼
Pod B (receives HTTP)

            In ambient mode, ztunnel handles mTLS on both hops.

            The waypoint receives already-decrypted traffic and

            makes L7 decisions. (In sidecar mode, Envoy handles

            mTLS directly — but that's not the case here.)

            

            mesh-waypoint must be in the AuthorizationPolicy

            allow list because it's the source identity that

            Pod B's ztunnel sees on hop 2.

            

            All traffic to a waypoint-labeled namespace goes

            through the waypoint — the routing decision is based

            on namespace/service labels, not traffic content.

            ztunnel doesn't inspect L4 vs L7; it checks labels.

        Deep dive: VirtualService vs HTTPRoute for traffic policy
        

          

            Two ways to configure traffic policy:


            VirtualService (Istio-native API)

              Retries, timeouts, fault injection, traffic splitting

              Mature, full-featured, widely documented

              Applied via the waypoint proxy (Envoy)


            HTTPRoute (Gateway API standard)

              Newer K8s-native approach

              Retry filters and timeouts are being added to the spec

              Gateway API is the long-term direction


            Both work through the waypoint. VirtualService is more

            feature-complete today. Gateway API is the future standard.
